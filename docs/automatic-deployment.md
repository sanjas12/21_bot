# Автоматическое развёртывание релизов

Workflow `.github/workflows/deploy.yml` запускается при публикации GitHub Release.
Черновики и prerelease не развёртываются. Тег должен иметь вид `1.2.3` или `v1.2.3`.
`scripts/release.sh` версии 0.3 публикует GitHub Release после отправки тега
и этим запускает автодеплой.

## Выпуск одной командой

На компьютере разработчика нужны Git, uv и GitHub CLI (`gh`).
Один раз выполните `gh auth login` и войдите в аккаунт с правом выпуска релизов.
В Windows запускайте скрипт из Git Bash: `bash scripts/release.sh`.
Перед запуском закоммитьте изменения. Скрипт обновляет основную ветку,
проверяет unittest и pre-commit, предлагает auto/PATCH/MINOR/MAJOR или ручную
версию и запрашивает подтверждение публикации с автодеплоем.
Auto выбирает MAJOR для breaking changes, MINOR для feat, иначе PATCH.
Версия берётся из `pyproject.toml`; `uv.lock` обновляется вместе с ней.
Новый тег имеет вид `vMAJOR.MINOR.PATCH`.

После создания коммита ветка и новый тег отправляются атомарно, затем
`gh release create --verify-tag --generate-notes` публикует релиз.
Если публикация не удалась после push, скрипт выводит команду для её повтора:
повторно повышать версию в этом случае не нужно.

## Первоначальная настройка

Сервер: Ubuntu с Bash, Git, `flock`, Python 3.11+, uv в `/root/.local/bin`,
проектом `/root/21_bot` и активной службой `21-bot.service`.
В каталоге проекта должны существовать `.env` и `data/calendar.sqlite3`.
Сервер должен иметь доступ к origin без интерактивного ввода пароля
(для приватного репозитория понадобится отдельный доступ сервера к GitHub).
SSH-порт сервера должен быть доступен GitHub-hosted runner.

В Settings → Secrets and variables → Actions задать repository secrets:

| Секрет | Значение |
| --- | --- |
| `DEPLOY_HOST` | IP-адрес или домен сервера |
| `DEPLOY_PORT` | SSH-порт, например `22` |
| `DEPLOY_USER` | `root` для текущей конфигурации |
| `DEPLOY_SSH_KEY` | Отдельный приватный ключ деплоя без passphrase |
| `DEPLOY_KNOWN_HOSTS` | Проверенная строка known_hosts для адреса и порта сервера |

Публичный ключ деплоя добавить в `/root/.ssh/authorized_keys`.
Для known_hosts взять публичный ключ из доверенного SSH-сеанса на сервере:
`cat /etc/ssh/ssh_host_ed25519_key.pub`.
Для порта 22 строка имеет вид `HOST ssh-ed25519 KEY`,
для другого порта — `[HOST]:PORT ssh-ed25519 KEY`.
HOST должен совпадать с DEPLOY_HOST. Приватные ключи в Git не добавлять.

## Выпуск

1. Закоммитить и отправить workflow, скрипт и остальные изменения в `main`.
2. Создать новый тег на коммите с этими файлами и отправить его в GitHub.
3. В Releases выбрать Draft a new release, указать этот тег и Publish release.
4. Открыть Actions → Deploy release и проверить результат.
5. Проверить `/start` и список событий в Telegram.

Workflow проверяет unittest и Ruff до подключения к серверу. Скрипт сверяет
коммит серверного тега с протестированным коммитом, запрещает обновление грязного
рабочего дерева и релизы, содержащие `.env`, `data/` или `.venv/` в Git.
Параллельные обновления блокируются в Actions и через серверный `flock`.

## Данные и восстановление

На время обновления бот недоступен. После остановки службы весь `data/`, `.env`
и предыдущий SHA копируются в `/root/21_bot-backups/deploy-XXXXXXXX`.
Затем переключается код на точный SHA релиза (detached HEAD), устанавливаются
зависимости `uv sync --locked --no-dev` и запускается служба.
`main` на сервере не передвигается; последующие обновления также выполняются по SHA.
Команды очистки каталога проекта не используются.

Проверка запуска наблюдает активность, PID и число перезапусков службы 20 секунд.
Она не подтверждает доступность Telegram: после первого деплоя проверьте бота вручную.
При ошибке после остановки выполняется попытка возврата предыдущего кода,
зависимостей и запуска службы. Если восстановление зависимостей не удалось,
служба остаётся остановленной для ручного восстановления.

База автоматически не заменяется резервной копией: после неудачного запуска
она уже могла принять новые события. При несовместимой миграции потребуется
ручное восстановление базы с остановленной службой. Перед будущими изменениями
схемы проверяйте совместимость отката. Резервные копии хранятся без автоматического
удаления; контролируйте свободное место.

Логи workflow доступны в GitHub Actions. Серверные логи:
`journalctl -u 21-bot.service -n 100 --no-pager`.
Перед пересылкой логов удаляйте токены и адреса подписок.
